01

Collaboration system

흩어질 규칙을 먼저
정하고 시작했습니다.

Challenge
프론트와 백엔드가 API 형태와 DB 스키마를 서로 다르게 이해할 위험이 있었습니다.
Action
설계 저장소를 단일 기준으로 삼고, 이슈 하나에 브랜치와 PR 하나를 연결하는 규칙을 제안했습니다.
Result
변경의 맥락을 저장소 기록만으로 추적하고, 새 구성원도 문서 한 곳에서 API를 파악할 수 있게 됐습니다.
02

Authorization design

권한을 관계 중심의
두 단계로 나눴습니다.

Challenge
공간 밖의 접근을 막는 일과 공간 안에서 남의 글을 수정하지 못하게 하는 일은 다른 문제였습니다.
Action
공간 구성원 여부를 먼저 확인하고, 수정·삭제 요청에는 작성자 본인인지 한 번 더 검증했습니다.
Result
역할 테이블을 늘리지 않고도 소속과 작성자 관계만으로 단순하고 명확한 인가 모델을 만들었습니다.
03

Frontend architecture

화면 코드에서
API 호출을 걷어냈습니다.

Challenge
요청 코드가 여러 화면에 흩어지면 주소나 인증 방식이 바뀔 때 수정 범위를 알기 어렵습니다.
Action
서버 호출을 src/api/ 아래 도메인별 모듈로 모으고 화면은 공개 함수만 사용하게 했습니다.
Result
API 주소와 인증 헤더 변경 지점이 한곳으로 모이고, 화면은 데이터 표현에 집중할 수 있게 됐습니다.
