# 12 — 실물 기기 등록에서 관측한 500과 그 대응

2026-09-11. 합성 인증기가 아니라 **실제 휴대폰**으로 등록·로그아웃·재로그인을 한 번
통과시켰다. 자동 테스트가 덮지 못하던 구간이고, 여기서 자동 테스트가 못 잡은 현상이
하나 나왔다.

## 관측한 순서

1. 휴대폰 브라우저로 공개 소개 페이지를 열고 `나만의 공간`으로 이동
2. 표시 이름은 합성값 그대로 두고 패스키 등록 시작
3. 기기 지문 인증 승인
4. **승인 직후 화면에 500이 표시됨**
5. 새로고침하자 `합성 사용자님의 나만의 공간`이 정상으로 열림
6. 로그아웃 후 같은 패스키로 다시 로그인 — 정상 통과

## 무엇이 일어난 것인가

**등록 자체는 성공했다.** 4번에서 실패한 것은 등록 요청이 아니라, 등록 성공 뒤
이동한 `/private` 화면이다. 근거는 세 가지다.

- `/private`는 `AuthenticationInterceptor`가 지킨다. 세션이 없으면 **401**을 내고
  컨트롤러까지 가지 않는다. 500이 나왔다는 것은 인증을 통과한 뒤 화면을 만드는
  단계에서 실패했다는 뜻이다.
- `AccountRegistrationService.finish`는 `@Transactional`이다. 계정·공개키·합성 자료
  3건이 한 트랜잭션으로 이미 커밋된 상태였다.
- 그래서 5번의 새로고침으로 바로 열렸고, 6번의 재로그인도 통과했다. 데이터가
  남아 있지 않았다면 둘 다 실패했어야 한다.

**정확한 원인은 확정하지 못했다.** Vercel 실행 로그를 확보하지 못했다. `/private`는
한 요청에서 비공개 자료·패스키 목록·CSRF 토큰을 모두 조회하므로, Supabase 연결이
그 순간 일시적으로 잡히지 않은 경우가 가장 그럴듯하지만 **추정이다.** 재현을 시도했으나
같은 경로에서 다시 만들지 못했다.

## 고친 것 — 에러 화면

원인을 확정하지 못했으므로 원인을 고쳤다고 적지 않는다. 대신 **같은 일이 다시 나도
읽을 수 있는 화면이 나오게** 했다.

`templates/error.html`이 없어서 500이 Spring 기본 Whitelabel Error Page로 나왔다.
페이지 톤에 맞는 안내와 새로고침 버튼을 가진 화면으로 바꿨고, 응답에 서버 내부 정보가
실리지 않도록 `application.properties`에 네 가지를 고정했다.

```properties
server.error.include-stacktrace=never
server.error.include-message=never
server.error.include-exception=false
server.error.include-binding-errors=never
```

`ErrorPageHttpTests`가 네 가지를 고정한다.

| 확인 | 내용 |
| --- | --- |
| 화면이 바뀌었다 | HTML 요청에 우리 화면이 나오고 `Whitelabel`이 없다 |
| 내부를 말하지 않는다 | 예외 메시지·예외 이름·패키지명·`java.`가 본문에 없다 |
| 비공개가 새지 않는다 | 합성 자료 세 건의 제목이 본문에 없다 |
| 경계가 그대로다 | 미인증 `/private`와 `/api/private-items`는 여전히 **401 JSON** |

마지막 줄이 중요하다. 에러 화면을 붙이면서 미인증 거절까지 HTML로 바뀌면 C17의
근거가 무너진다. 인터셉터는 `sendError`가 아니라 응답에 직접 쓰므로 에러 화면으로
넘어가지 않고, 그 사실을 테스트로 고정했다.

전체 테스트 **42개 통과**.

## 남는 것

원인 미확정이 그대로 남는다. `T08-AUTH-GUIDE.md` ⑥에 적었다. 등록 직후 첫
`/private` 요청이 간헐적으로 실패할 수 있고, 지금 할 수 있는 것은 실패를 읽을 수 있게
만드는 것까지다.

## 뒤이어 고친 것 — 목록이 저장 위치를 말한다

이 관측에서 두 번째 문제가 드러났다. **등록을 직접 한 사람이 어디에 저장됐는지 몰랐다.**
C26의 답을 얻으려고 휴대폰 설정 앱을 뒤져야 했다.

그런데 서버는 이미 알고 있었다. 등록 응답이 두 신호를 함께 주고, 둘 다 저장되고 있다.

| 저장된 값 | 무엇을 말하나 |
| --- | --- |
| `backupEligible` | true면 동기화형(구글 비밀번호 관리자·iCloud), false면 기기 전용 |
| `transports` | `internal` 이 기기 · `hybrid` QR로 연결한 다른 기기 · `usb`/`nfc`/`ble` 보안 키 |

`PasskeyView`가 `(id, nickname, registeredAt)`만 내보내고 있어서 화면까지 오지 못했다.
`PasskeyStorage`를 만들어 두 값을 사람의 말로 바꾸고, 목록의 각 행에 붙였다.

```text
내 휴대폰    2026-09-11   [동기화됨 · 이 기기]
집 PC       2026-09-11   [이 기기 전용]
```

둘 다 인증기를 설명하는 값이지 키 자체가 아니다. 공개키·credential ID와 마찬가지로
비밀이 아니다.

### 라벨 규칙에서 걸린 것 두 가지

처음 구현은 `이 기기 전용 · 이 기기`를 만들어 냈다. 같은 말을 두 번 한다.
`이 기기 전용`이 이미 기기를 지목하므로 뒤를 붙이지 않는다.

더 중요한 것은 안드로이드가 구글 비밀번호 관리자 패스키 하나에 `internal`과 `hybrid`를
**함께** 보고한다는 점이다. 여기서 만들어졌고 다른 기기에서 QR로도 닿을 수 있다는 뜻이다.
두 행을 구분해야 하는 사람에게는 **어디서 만들었는지**가 더 쓸모 있으므로 `internal`이
이긴다. 보안 키는 그 자체가 답이라 다른 말을 붙이지 않는다.

`PasskeyStorageTests`가 이 규칙을 고정한다. 전체 테스트 **50개 통과**.

### 과제와의 관계

- **C26** 저장 위치를 화면이 스스로 보여 준다. 제출문의 진술과 화면이 같은 것을 가리킨다.
- **C43** 목록에 이름·등록일에 더해 저장 위치가 보인다.
- **카드 4** 어느 패스키를 지울지 판단할 근거가 생겼다. 삭제는 되돌릴 수 없다.

## C26 — 저장 위치 확인 (2026-09-11)

배포 반영 뒤 같은 휴대폰으로 다시 들어가 목록을 확인했다.

```text
내 휴대폰    2026-09-11    [동기화됨 · 이 기기]
```

같은 세션에서 뜬 Google 비밀번호 관리자 창이 같은 것을 가리킨다. 창에는 구글 로고와
`t08-passkey-portfolio.vercel.app`, 그리고 계정명이 표시된다.

**저장 위치는 `Google 비밀번호 관리자`다.** 기기 자체도 보안 키도 아니다.
`동기화됨`은 `backupEligible`이 참이라는 뜻이고, 이는 구글 계정에 백업되어 다른 기기에서도
쓸 수 있는 자격증명임을 말한다. `이 기기`는 `transports`에 `internal`이 있다는 뜻으로,
이 휴대폰에서 만들어졌다는 것이다.

확인 환경은 안드로이드 · 크롬이다.

### 실명이 들어가지 않은 것도 화면에 남는다

구글 창이 표시하는 계정명은 `synthetic-` 로 시작하는 합성 식별자다. 표시 이름을 합성값
그대로 둔 결과가 운영체제 수준의 자격증명 목록까지 이어진다. 등록 어느 단계에도 실명·연락처가
들어가지 않는다는 것이 서버 기록만이 아니라 기기 화면으로도 확인된다.
