# T08 제출문

## 제출 URL

- 결과물 HTTPS URL: `https://t08-passkey-portfolio.vercel.app`
- 소스 HTTPS URL: `https://github.com/myeongjundev/t08-passkey-portfolio`

## 짧은 확인 방법

1. 어디로 가나요: 결과물 URL의 공개 소개 첫 화면에서 `나만의 공간`으로 이동합니다.
2. 세 단계 안에 무엇을 하나요: 합성 이름 입력 → 패스키 만들기(기기 지문 인증) → 비공개 자료 3건 확인.
3. 무엇이 보이면 통과인가요: 지문 인증 창이 뜨고, 통과 후 패스키 이름·등록일, 합성 비공개 자료, 두 번째 패스키 관리가 보이면 통과입니다.
4. 안 될 때는 무엇이 보이나요: 취소·검증 실패 안내 또는 미인증 요청의 401 응답이 보입니다.

## AI와 내 판단

1. AI에게 맡긴 일: 요구사항 정리, WebAuthn 연결 초안, 테스트와 증거 문서 작성을 맡겼습니다.
2. 내가 직접 판단한 일: 비밀번호 없는 공개 등록, 서버 세션, 마지막 패스키 삭제 금지와 합성 데이터 정책을 결정했습니다.
3. 따르지 않은 제안: T07의 비밀번호·JWT 방식을 재사용하지 않았습니다. T08은 개인키가 기기를 떠나지 않는 패스키 과제이기 때문입니다.

## 잠금 해제 수단 — 기기 지문

비밀번호는 만들지 않았고, 등록과 로그인 모두 **기기의 지문 인증**을 거쳐야 합니다.
등록·로그인 options를 `userVerification: "required"`로 내려보내고, 서버 검증에서도
`userVerificationRequired=true`로 다시 확인하므로 지문을 건너뛴 요청은 거절됩니다.
Windows Hello는 지문, 맥은 Touch ID, 휴대폰은 지문·얼굴이 이 자리를 담당합니다.

지문 자체는 기기를 벗어나지 않습니다. 지문은 기기 안의 개인키를 여는 열쇠로만 쓰이고,
서버가 받아 저장하는 것은 공개키·credential ID·sign counter뿐입니다. 서버에는 생체정보도
비밀번호도 개인키도 저장되지 않습니다.

## 패스키 저장 위치

등록한 패스키는 **Google 비밀번호 관리자**에 저장되었습니다. 기기 자체나 보안 키가
아니라 구글 계정에 묶인 동기화형 패스키입니다.

- 확인 환경: 안드로이드 · 크롬
- 확인 날짜: 2026-09-11
- 화면 근거: 패스키 목록의 `동기화됨 · 이 기기` 배지, 그리고 등록·로그인 때 뜨는
  Google 비밀번호 관리자 창

저장 위치는 제출문의 진술만이 아니라 **화면이 스스로 보여 줍니다.** 등록 응답이 주는
`backupEligible`과 `transports`를 그대로 목록에 표시하므로, 심사하는 사람이 따로
기기 설정을 열어 볼 필요가 없습니다. `동기화됨`은 구글 계정에 백업된다는 뜻이고,
`이 기기`는 이 휴대폰에서 만들어졌다는 뜻입니다.

동기화형을 고른 이유는 카드 4의 요구와 맞물립니다. 기기 전용 패스키는 그 기기를 잃으면
되찾을 수 없고, 이 시스템에는 비밀번호·이메일 복구가 없습니다. 동기화형은 구글 계정으로
새 기기에서 복구됩니다. 대신 구글 계정이 단일 실패점이 된다는 맞바꿈이 있습니다.

구글이 표시하는 계정명은 `synthetic-…` 형태의 합성 식별자입니다. 실명·연락처는 등록
과정 어디에도 들어가지 않습니다.

## 완주 확인

- 공개 첫 화면은 등록 없이 열립니다.
- 비공개 자료는 인증 전 HTML과 API 응답에 포함되지 않습니다.
- 서버에는 공개키·credential ID·sign counter만 저장하고 비밀번호와 개인키는 저장하지 않습니다.
- 등록·로그인 모두 기기 지문 인증(사용자 확인)을 거치며, 지문 데이터는 서버로 전송·저장되지 않습니다.
- 로그인은 저장 공개키 서명 검증 뒤 서버 세션으로 유지합니다.
- 로그아웃, challenge 재사용, 삭제한 패스키, 양방향 타 계정 조회가 거절됩니다.
- 세션·CSRF·challenge·서명 값은 제출 증거에서 가렸습니다.
